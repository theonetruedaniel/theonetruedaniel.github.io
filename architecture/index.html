The system being built

One place to direct work. One core record of what happened.

A personal platform for research, coding, planning, and documents. The design keeps projects, memory, permissions, and run history under Abrams Intelligence’s control as models and optional tools change.

  1. 01 · Direct

    Personal workspace

    Choose a task, project context, and the outcome to review.

  2. 02 · Authorize

    Abrams Core

    Own grants, budgets, durable runs, audit, and external effects.

  3. 03 · Execute

    Replaceable adapters

    Use an admitted model, agent runtime, or tool within that task’s boundaries.

  4. 04 · Reconcile

    Evidence & review

    Return a traceable result; preserve the record through retries, reconnects, and Stop.

Planned application architecture. The functioning Core and product UI have not been implemented.

How task routing fits the design

Product model router · planned

Provider-neutral, with admitted cloud and local routes. Manual choice takes precedence; automatic selection must respect task risk, permissions, compatibility, and budget. Switching a model must preserve project state and memory.

Development dispatcher · implemented offline

Separate Codex development tooling proposes Luna for routine work, Sol for implementation and synthesis, and Astra for consequential architecture or security work. These are starting policy heuristics, not proven quality rankings or savings. Live editing remains unqualified.

M01 · Architecture design

Intent & task design

Maps research, coding, planning, or document work into a bounded, inspectable plan before a model path is selected.

Relationships

  • Receives scope from the personal platform shell.
  • Defines the handoff to model and tool design.

Design decisions

  • Route by task risk and scope.
  • No implicit tool access.
Engineering choices · planned bake-offs

Choose the smallest option that passes the job.

Compare candidates on the same frozen inputs, model route, permissions, and resource envelope. Keep failed runs and recovery evidence. A familiar tool or a fast response does not earn adoption by itself.

BO-01 · planned comparison

Does a desktop shell earn its complexity?

Tauri 2 with React / TypeScript versus a contract-equivalent local web or PWA shell, driven by the same mock Core event stream.

Evaluate
Keyboard access, approval and Stop visibility, crash / reconnect behavior, startup, and process resources.
Decision rule
Choose Tauri only when demonstrated native value passes the gates. Keep the web / PWA path as the fallback.
Current evidence
Planned comparison. No completed shell bake-off or product UI is claimed.
What makes a comparison fair?

Preregister the hypothesis, corpus, thresholds, failures, and decision owner. Pin the exact artifacts and adapters. Use identical context, grants, budgets, retries, and recovery cases. Score quality, safety, privacy, latency, resources, cost, recovery, and maintenance separately. Adopt only the exact scope that passed and record the decision.
